# 需求文档 → 开发计划

将需求文档分析转化为结构化的开发计划，每项计划仅包含**标题**和**验收标准**，按合理的逻辑顺序排列。

## 工作流程

### 第一步：读取需求文档

用户提供文件路径后，使用 Read 工具读取文件内容。支持常见文档格式：
- Markdown（.md）
- 纯文本（.txt）
- Word 文档（.docx）—— 如遇乱码，提示用户转换为 md 或 txt

如果文件不存在或无法读取，直接告知用户并请求提供正确的路径。

### 第二步：初步分析，识别待确认点

通读全文后，整理出以下信息：
1. **核心功能列表** —— 文档中明确提到的所有功能点
2. **模糊/歧义点** —— 以下情况视为待确认：
   - 同一概念有多种解读方式
   - 缺少关键细节（如：数据来源不明确、交互方式未描述、边界条件未定义）
   - 两处描述存在矛盾
   - 技术术语或业务术语含义不清
   - 未指定优先级或范围界限

将模糊点按重要程度排序（影响核心流程的优先），准备逐个提问。

### 第三步：逐个提问澄清

一次只提一个问题，等待用户回复后再提下一个。每个问题应：

- **明确指出**文档中哪段内容引发了疑问（引用原文或指明位置）
- **列出所有可能的解读**，供用户选择或参考
- 如果涉及核心决策，说明不同选择对后续计划的影响

用户回复确认后，将结论记录（可记入 memory），再继续下一个问题。重复直到所有疑问澄清完毕。

**如果在分析中没有发现任何模糊点**（极为罕见），直接进入第四步，但需要在输出中注明"未发现需要澄清的内容"。

### 第四步：生成开发计划

根据需求文档和用户确认的结论，按以下规则输出开发计划。

## 输出格式

```org
* TODO [标题]
    验收：
    - [可验证的条件 1]
    - [可验证的条件 2]

* TODO [标题]
    验收：
    - [可验证的条件 1]

* TODO [标题]
    验收：
    - [可验证的条件 1]
```

## 输出规则

### 标题
- 以动词开头，简洁描述要完成的工作（如"搭建项目脚手架"、"实现用户登录功能"、"对接支付接口"）
- 一词概括，避免过长
- 测试类计划使用明确的测试类型前缀，如"功能测试——"、"接口联调测试——"、"端到端测试——"，不得使用笼统的"开发者测试——"

### 验收标准
- 每条标准必须是**可验证的、具体的**，不能是模糊描述
- 用"用户能..."、"系统支持..."、"当...时..."开头
- 每条标准独立可测，不需要额外解释
- 只写验收条件，不写实现方法

坏例（太模糊）：
- "登录功能正常" ← 什么叫正常？无法验证

好例（可验证）：
- "用户输入正确的邮箱和密码后，能成功登录并跳转到首页"
- "用户连续输入错误密码 5 次后，账号被锁定 15 分钟"

### 关联性
- 计划按自然执行顺序排列，编号靠前的优先执行
- 相邻计划之间应有承接关系，整个列表形成一条清晰的**从基础到完整**的构建路径
- 属于同一功能模块的计划，用相同前缀标注，如"用户模块：注册"、"用户模块：登录"

## 补充规则

- **不做过度拆分**：如果一个功能只需一步完成且验收标准少于 3 条，不要强行拆分
- **不做过度合并**：如果一个计划项的验收标准超过 5 条，考虑是否应该拆分
- **不添加需求文档中没有的功能**：只输出文档中明确要求或合理推断出的内容。如果推断的内容不确定，回归第三步提问确认

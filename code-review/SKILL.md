# Code Review 技能

对代码变更进行系统化审查，输出结构化报告，附带修复建议和影响范围分析。

## 审查流程

### 1. 确定审查范围

按以下优先级确定待审查的代码：

1. 用户明确指定的文件路径
2. `git diff --name-only` 获取未暂存变更
3. `git diff --cached --name-only` 获取已暂存变更

```bash
git diff --name-only
git diff --cached --name-only
```

只审查源代码文件，跳过以下内容：
- 构建产物：`dist/`、`build/`、`node_modules/`
- 配置文件：`.json`、`.lock`、`.yaml`、`.yml`、`.toml`
- 静态资源：图片、字体、`.svg`
- 自动生成文件：`.d.ts`（无对应 `.ts` 变更时）

如果变更文件超过 10 个，提示用户缩小审查范围。

### 2. 读取变更内容

对每个变更文件：

```bash
git diff <file>        # 未暂存变更
git diff --cached <file>  # 已暂存变更
```

如果 diff 超过 300 行，先阅读完整文件了解上下文，再聚焦 diff 区域。

### 3. 逐文件审查

从以下三个维度审查每个变更：

#### 代码质量

| 检查项 | 说明 |
|--------|------|
| 命名 | 变量/函数/类名是否准确表达意图，是否遵循语言惯例 |
| 冗余 | 是否有无用变量、死代码、重复逻辑 |
| 简洁性 | 是否有可简化的复杂表达式；三行内重复模式是否应抽取 |
| 过度抽象 | 单次使用的代码是否被不必要地封装 |
| 可读性 | 逻辑是否一眼能看懂，嵌套是否过深（>3 层） |
| try-catch 嵌套 | try-catch 内部不得再次包裹 try-catch；如确有必要，必须注释说明内层 try-catch 的用途 |

#### 性能

| 检查项 | 说明 |
|--------|------|
| 循环内开销 | 循环中是否有重复计算、I/O 操作、数据库查询 |
| N+1 查询 | 是否在循环内逐条查询数据库或调用 API |
| 不必要分配 | 是否创建了大对象但未使用，或频繁创建短生命周期对象 |
| 数据结构 | 是否可用 Set/Map 替代 Array 的线性查找 |
| 阻塞操作 | 异步上下文中是否存在同步阻塞调用 |

#### 逻辑正确性

| 检查项 | 说明 |
|--------|------|
| 边界条件 | 空数组、空字符串、0、null/undefined 是否处理 |
| 错误处理 | 异常是否被静默吞掉，错误信息是否明确 |
| 竞态条件 | 异步操作的结果到达顺序是否会影响状态正确性 |
| 类型安全 | 类型断言是否安全，是否存在隐式类型转换风险 |

## 输出格式

使用以下固定模板输出审查报告：

```
# Code Review 报告

## 审查概览
- 审查文件：N 个
- 严重问题：N 个
- 警告问题：N 个
- 建议：N 个

## 问题列表

### 严重 🔴 — 必须修复，会导致功能异常或严重性能问题

**[严重] 问题标题**
- 文件：`path/to/file.ts:行号`
- 类型：代码质量 / 性能 / 逻辑正确性
- 描述：具体说明问题是什么
- 修复建议：
\```语言
// 修复前
原代码
// 修复后
建议代码
\```
- 影响范围：说明可能影响的其他模块或场景

### 警告 🟡 — 建议修复，影响可维护性或轻微性能

（同上格式）

### 建议 🟢 — 可选优化，改善可读性或代码风格

（同上格式）
```

### 严重程度判定标准

| 级别 | 判定标准 |
|------|----------|
| 严重 🔴 | 功能异常、数据错误、严重性能问题（>50% 性能损失）、明确会抛异常 |
| 警告 🟡 | 边界条件遗漏、潜在 bug、N+1 查询、可维护性问题 |
| 建议 🟢 | 命名改进、简化写法、风格统一、轻度性能优化 |

### 报告原则

- 没有发现问题就直接说"未发现问题"，不要编造
- 每条问题必须具备：文件路径 + 行号、描述、修复建议
- 修复建议给出前后对比代码，而非文字描述
- 相同模式的问题合并到一条，列出所有出现的文件
- 不在报告中对用户的选择做主观评判，只陈述技术事实
